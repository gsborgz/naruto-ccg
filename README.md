# Naruto CCG Digital

Esse projeto é uma versão digital do clássico Naruto CCG (publicado entre 2006 a 2013 pela Bandai). A ideia do projeto é funcionar como um "Pokemon TCG Live" para Naruto CCG, que possa ser rodado diretamente no navegador, já que a ideia é usar para jogar entre amigos.

Hoje o app tem o catálogo de cartas e o montador de decks: o jogador monta quantos decks quiser com as cartas disponíveis, seguindo as regras de montagem do jogo original. Os decks ficam no localStorage do navegador e podem ser compartilhados por um código (UUID) gravado num banco simples, como no projeto pokedex.

Publicado em <https://naruto-ccg.vercel.app> (deploy automático a cada push na `main`). O acesso é protegido por senha quando a variável `SITE_PASSWORD` existe: o navegador pede uma vez (`/entrar`) e guarda o acesso num cookie de 1 ano (`src/middleware.ts`, `src/lib/sitePassword.ts`; ver [docs/DEPLOY.md](docs/DEPLOY.md#senha-de-acesso)).

Na pasta `docs/` estão os manuais oficiais (PDF), as regras consolidadas (`docs/REGRAS.md`), o guia de publicação (`docs/DEPLOY.md`), o processo de revisão das cartas contra as imagens e das frases (`docs/REVISAO-CARTAS.md`), as convenções da tradução PT-BR (`docs/TRADUCAO.md`) e a especificação da próxima etapa, as salas de jogo (`docs/SALAS.md`).

A ideia futuramente é ter um layout dinâmico para as cartas, com o sistema "montando" a carta virtualmente usando o layout + ícones + descrições + tipagens + efeitos. Por enquanto as cartas usam as imagens oficiais, com tipos, custos e efeitos cadastrados.

## Como rodar

Requer Node.js e Docker (para o Redis local).

```bash
npm install
cp .env.example .env.local   # só na primeira vez
npm run dev                  # sobe o Redis local (Docker) e o app em http://localhost:3000
npm test                     # regras de montagem, conversões das cartas, compartilhamento e salas (com cartas inventadas)
npm run type-check
npm run services:down        # derruba o Redis local
npm run cards:layouts        # recria public/card-layouts a partir de card-layouts/ (molduras e ícones do criador de cartas e artes das cartas escaneadas)
npm run content:sync-cards -- S02   # copia cartas de src/data/sets/ (+ tradução) para o conteúdo no Redis (ver "Conteúdo do jogo")
npm run content:push         # envia o conteúdo do Redis local para o de produção, de uma vez (ver "Conteúdo do jogo")
```

Com o Redis local vazio, a primeira abertura do app grava nele a carga inicial (as cartas de `src/data/sets/` e os layouts e ícones de `src/lib/cardMaker/`).

Publicação (Vercel + Upstash): ver [docs/DEPLOY.md](docs/DEPLOY.md).

## Funcionalidades

- **Cartas** (`/cards`): catálogo com busca por nome, característica ou efeito, filtros por coleção, tipo e elemento, ordenação e detalhe de cada carta. No celular, a busca fica presa no topo com o botão **Filtros** (coleção, tipo, elemento, ordenação e design num painel que sobe de baixo) e os filtros ativos aparecem como chips removíveis. Mostra as imagens originais; o toggle **Originais | Montadas** passa para as cartas montadas em tempo real.
- **Meus decks** (`/`): criar, editar, duplicar, excluir, compartilhar e importar decks.
- **Jogar** (`/jogar` e `/salas/<uuid>`): criar uma sala só com o apelido, enviar o código (ou o link) para um amigo e, dentro da sala, cada um escolhe o deck e marca **Pronto**. Quando os dois estão prontos, a sala abre a **arena** com os decks embaralhados e a mão inicial: cada um arrasta as próprias cartas entre as zonas, compra, embaralha e busca cartas no deck. Quem começa é sorteado; o Atacante avança as fases (Missão, Organização e Batalha, com **Próxima fase**) e **passa o turno** na Batalha, o que avança o Marcador de Turnos dele (as fases são só referência, sem as regras de cada uma). Ninjas podem ser virados para Ferido (tecla **R** sobre o Ninja; as teclas de atalho ficam no botão **⌨ Atalhos**), o Poder de cada Time pode ser ajustado com −/+, as cartas na mesa recebem moedas (Growth, +1/+1, Poison, as das Missões Permanentes (X) e qualquer outra impressa; as de Poder somam no Time), a **🪙 Moeda** Ninja é sorteada no servidor para os dois verem, o Marcador de Turnos tem −/+, Prêmios de Batalha podem ser devolvidos (↩), cartas do topo ou do fundo do Deck podem ser reveladas na Vila (👁) e clicar numa carta sua abre o detalhe com **Descartar** e os botões de mover. A tela segue o design "Campo de Jogo" (palco de 1600×900 escalado para caber inteiro na janela). Prévia local em `/arena`. **Jogar sozinho** (`/jogar/sozinho`): um deck para cada lado e o jogador comanda os dois, no próprio navegador (**⇅ Trocar de lado**, automático ao passar o turno). Detalhes em [docs/SALAS.md](docs/SALAS.md).
- **Criar carta** (`/criar`): monta cartas nos layouts 1 a 5 a partir das molduras e ícones de `card-layouts/` (tipo, elementos, custos, vila, Atributo de Combate com o kanji tirado de `card-layouts/icons/attributes`, força, textos e frase), com a arte enviada pelo jogador (arraste para enquadrar). Dá para partir de uma carta do catálogo (**Importar do catálogo** ou `/criar?importar=<id>&layout=layout-02`) e comparar com a imagem original. As edições ficam num rascunho e só são gravadas no botão **Salvar**, que guarda a carta no localStorage (`naruto-ccg:custom-cards`) e envia a arte para o Vercel Blob; sair com alterações não salvas pergunta o que fazer, como no montador. Cada layout tem a sua configuração (no conteúdo do jogo, no Redis; ver "Conteúdo do jogo"), onde cada ícone tem só a posição e o tamanho (`{ x, y, size }`); o resto do ícone (proporção, nome de lado, números de custo e de força, nome e kanji do atributo) fica na configuração de cada ícone, relativa ao próprio ícone, para ficar igual em todos os layouts. A página `/criar/calibrar?layout=layout-02&ids=...` mostra lado a lado a carta montada, a original e as duas sobrepostas. **Editar layouts** (`/criar/layouts`, link no Criar carta) edita essas configurações, para todo mundo e sem deploy, em duas abas. **Layouts**: escolhe o layout, o tipo e uma carta de exemplo (com a original por cima), arrasta as caixas de cada ícone e texto na carta (o canto muda o tamanho; as setas movem a selecionada) ou mexe nos campos; muda o nome do layout, os ícones que ele usa por padrão (variante dos elementos, custos de entrada e de mão, moldura do Atributo de Combate) e as imagens (moldura e painel de cada tipo). **+ Novo layout** cria um layout cópia do aberto (molduras, painéis, posições e ícones), com id `layout-<nome>`; enquanto uma imagem dele ainda é a do layout base, **Trocar imagem** grava a nova em `<id do layout>/` e o layout passa a usá-la. **Excluir layout** (só os criados no editor, e só se nenhuma carta o usa) apaga o layout e as imagens dele do Blob (`src/app/api/content/layouts/`). **Ícones**: cada ícone (tipo, tipo alternativo, elemento, custo, Chakra, Atributo de Combate) numa carta de exemplo, só com as caixas de dentro dele, e os campos dele (posição, tamanho e cor dos textos e números, contorno, sombra), que valem em todos os layouts (`src/components/cardMaker/IconsEditor.tsx`). **Trocar imagem** troca a moldura, o painel ou a imagem de um ícone (WebP ou PNG, até 2 MB, para o Vercel Blob; a anterior é apagada de lá); a imagem nova precisa ter o tamanho padrão, o da imagem que ela substitui (molduras e painéis 1060×1484, tipo 360×360, custo 220×202, Atributo de Combate 680×670; o editor mostra o de cada uma e recusa outro tamanho, para quem envia redimensionar antes). **Voltar para a do deploy** apaga do Blob a imagem trocada, e **Histórico** volta uma das últimas 5 versões de um layout, ícone ou carta (as imagens não têm histórico: no Blob só fica o que está em uso, ver "Conteúdo do jogo"). Um valor igual em vários tipos de carta (no código original, `forAllTypes` e constantes) muda em todos eles (`linkSharedTypes` em `src/lib/content/changes.ts`). O **Salvar** grava via `/api/content/config`. O detalhe de toda carta do catálogo tem a aba **Editar** (`src/components/cardMaker/CardEditTab.tsx`): o mesmo editor do criador (layout, design, ícone do tipo, elementos e variantes, nome, tamanho e quebra de linha do nome, texto com a marcação, frase e sombreado, características, vilas, custos e ícones de custo, força, Atributo de Combate, artes e enquadramento, com a original por cima), na carta convertida para carta do criador e de volta (`src/lib/cardMaker/catalogEdit.ts`). O **Salvar** grava a carta inteira no conteúdo do jogo (`PUT /api/content/cards/<id>`, conferida em `src/lib/content/cardValidation.ts`): os dados de jogo e os textos na carta, o visual no `layout` dela (o texto com a marcação, o nome com quebra de linha e as vilas só quando diferem do que sai dos dados). Uma arte enviada vai para o Vercel Blob e conta como usada pela carta (`catalog:<id>`). O link **editar o layout** abre o editor de layouts no layout e na carta. Na carta montada do detalhe, o atalho **Tamanho do nome** grava o ajuste do nome (`/api/content/cards/<id>/layout`). Qualquer um com a senha do site pode editar.
- **Montador** (`/decks/<id>`): cartas disponíveis à esquerda, com +/− em cada uma, e o deck à direita (por tipo, mais as abas Reforço e Tokens, com contagem e validação das regras). No celular, o deck fica numa barra presa embaixo (contagem e validade); tocar nela abre o deck num painel que sobe de baixo, por cima da lista, e ao fechar a lista continua no mesmo ponto (`src/components/DeckSheet.tsx`).
  - **Imprimir deck** gera um PDF A4 (9 cartas por folha, tamanho real). O seletor **Design** vale para o deck inteiro: **Original** (a imagem impressa) ou **Remontado** (a carta montada, no idioma escolhido, nas cartas já escaneadas; as outras saem com a impressa). As cartas criadas saem sempre montadas. A escolha fica no localStorage (`naruto-ccg:print-design`); o desenho das montadas fica em `src/components/cardMaker/cardImageRenderer.tsx`.
  - As cartas do **Criar carta** também aparecem (coleção **Cartas criadas** no filtro) e seguem as mesmas regras de montagem, lidas dos campos do criador (`src/lib/cardMaker/deckCard.ts`; no deck, o id é `custom-<id da carta>`). Decks com cartas criadas podem ir para as salas e ser compartilhados por código: as cartas vão junto com o deck e as artes ficam no Vercel Blob (ver [docs/SALAS.md](docs/SALAS.md#cartas-criadas) e [docs/DEPLOY.md](docs/DEPLOY.md#artes-das-cartas-criadas-vercel-blob)). Toda arte enviada é tratada antes (até 1050 px, WebP, até 300 KB). O detalhe da carta tem **Excluir carta permanentemente**: ela sai do criador e dos decks, e a arte é apagada do Blob se nada mais a usa. O detalhe da carta tem o link **Editar no criador** (`/criar?carta=<id>`).
  - As alterações ficam num rascunho e só são gravadas no botão **Salvar**.
- **Artes alternativas** (detalhe da carta, no catálogo e no montador): a aba **Arte** do detalhe mostra a original e as artes enviadas por qualquer jogador para aquela carta. **+ Nova arte** monta a arte como no criador, no layout identificado para a carta: o **fundo** (atrás da moldura, obrigatório) e a **frente** (opcional, na frente da moldura e atrás do painel, com transparência), cada uma com imagem, zoom, horizontal, vertical e **Centralizar**, arrastando na carta (as duas juntas ou uma só). As imagens são tratadas (até 1050 px, WebP, até 300 KB; a frente guarda a transparência) e, no **Salvar arte**, vão para o Vercel Blob e a arte fica disponível para todo mundo (`AltArtPlacement`: o fundo e `front`). A edição só vale nas cartas já mapeadas (com `layout`, `canEditAltArt`, conferido também na API); nas outras coleções a aba avisa que a arte ainda não pode ser trocada. Cada jogador escolhe a arte de cada carta no próprio navegador (localStorage `naruto-ccg:art-choices`); com uma arte escolhida, a carta aparece montada com ela na listagem, no montador e nas partidas, onde o oponente também a vê (ver [docs/SALAS.md](docs/SALAS.md#artes-alternativas)). Só quem enviou a arte pode removê-la (as duas imagens saem do Blob, a não ser que outra arte ou carta criada use o mesmo arquivo). As artes ficam no Redis em `naruto-ccg:alt-arts:<id da carta>` (`src/lib/altArts.ts`, `src/lib/altArtStore.ts`, `src/app/api/alt-arts/`, `src/components/AltArtPicker.tsx`). A impressão do deck continua usando a original ou a remontada.
  - Ao sair com alterações não salvas (links do app ou "voltar" do navegador), o app pergunta se quer **Salvar**, **Descartar** ou continuar editando. Ao fechar ou recarregar a aba, aparece o aviso padrão do navegador.

## Compartilhar decks

Os decks ficam no localStorage. Para passar para outro navegador ou para um amigo, a tela **Meus decks** tem:

- **Compartilhar** (em cada deck) e **Compartilhar coleção** (todos os decks): enviam uma cópia para o servidor, que grava no Redis e devolve um UUID.
- **Importar**: busca o UUID e adiciona os decks como novos (não apaga nada).

O código é um retrato do momento: editar o deck depois não muda o que foi compartilhado. Mesmo esquema do projeto pokedex: `@upstash/redis` (API REST da Upstash); local via `compose.yaml` (Redis + `serverless-redis-http` nas portas 6381/8078).

- O cliente lê `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` **ou** `KV_REST_API_URL`/`KV_REST_API_TOKEN`. Em produção são as `KV_*`, criadas pela integração Upstash da Vercel.
- O banco de produção é **compartilhado com o projeto pokedex**, então toda chave gravada começa com `naruto-ccg:` (ex.: `naruto-ccg:share:<uuid>`). Mantenha esse prefixo em chaves novas.
- Código: `src/app/api/shares`, `src/lib/deckShare.ts` (validação), `src/lib/shareClient.ts`, `src/lib/redis.ts`.

## Conteúdo do jogo

As cartas (dados de jogo e o `layout` de cada uma), a configuração dos layouts e dos ícones e as imagens das molduras e ícones ficam fora do código, para serem editadas pelo site sem deploy (`src/lib/content/`):

- **Redis** (chaves `naruto-ccg:content:*`): `cards` (hash id → carta; o campo `set` é o código da coleção, um dos de `src/data/sets.ts`), `layouts` (hash id → configuração do layout), `icons` (hash `<grupo>:<id>` → configuração do ícone, ex.: `element:fire-02`), `assets` (hash caminho da imagem → URL no Vercel Blob), `version` (aumenta a cada gravação) e `history:<tipo>:<id>` (as últimas 5 versões de cada carta, layout e ícone, para o **Histórico** dos editores).
- **Imagens:** a configuração guarda o caminho lógico (`/card-layouts/layout-02/jutsu-frame.webp`) e o mapa `assets` diz onde a imagem está no Blob (`naruto-ccg/card-layouts/<caminho>-<hash>.webp`, `src/lib/content/assetStore.ts`). Sem entrada no mapa, vale o arquivo de `public/card-layouts/` do deploy. **Enviar imagens do deploy para o Blob** (no editor de layouts) copia todas para o Blob de uma vez. Quem resolve o caminho é `assetUrl` (`src/lib/content/assets.ts`), usado pela carta montada.
- **Nada sobrando no Blob:** só fica guardada a imagem em uso. Trocar uma imagem de layout ou ícone apaga a anterior (por isso as imagens não têm histórico), **Voltar para a do deploy** apaga a trocada, e um envio que falhou no meio é apagado; **Apagar imagens sem uso** (no editor de layouts, e no fim do envio das imagens do deploy) apaga da pasta `naruto-ccg/card-layouts/` o que não está no mapa. As artes (`naruto-ccg/art/`, das cartas criadas e das artes alternativas) contam quem as usa (`naruto-ccg:art-refs:<sha256>`, `src/lib/artStore.ts`): a imagem sai do Blob quando a última carta criada ou arte alternativa que a usa troca de arte ou é excluída, e a enviada que ninguém passou a usar em 24 h é apagada.
- **Carga:** o navegador busca a versão em `/api/content` e o conteúdo em `/api/content/<versão>` (~2,8 MB, em cache para sempre no navegador e na CDN) antes de mostrar as telas (`ContentProvider`); os módulos `CARDS`/`CARDS_BY_ID` (`src/data/cards.ts`), `LAYOUTS` e os mapas de ícones começam vazios e são preenchidos no lugar (`hydrateContent`). No servidor, toda rota que usa o catálogo chama `ensureContent()` (`src/lib/content/server.ts`, que confere a versão no Redis no máximo a cada 15 s).
- **Carga inicial:** `src/data/sets/` (cartas) e os `seed.ts` de `src/lib/cardMaker/layouts/` e `icons/` (configuração calibrada) só servem para gravar o Redis quando ele está vazio e para os testes (`src/lib/content/testSetup.mts`). O app não lê esses arquivos. As cartas são gravadas com os textos em PT-BR (`cardsToPtBr` em `src/lib/content/ptbr.ts`: a tradução de `src/data/ptbr/` e o glossário). Corrigiu uma carta neles (revisão contra as imagens)? Leve para o Redis com `npm run content:sync-cards -- <SET ou ids>` (mantém o `layout` do Redis, a não ser com `--with-layout`; troca os dados e os textos, inclusive o que foi editado pelo site, e a versão anterior vai para o histórico; `--dry-run` só mostra o que mudaria). O formato do conteúdo fica em `naruto-ccg:content:format` (2 = textos em PT-BR); um Redis com o formato antigo (textos em inglês) é convertido na primeira leitura.
- **Enviar para produção:** `npm run content:push` envia de uma vez o que mudou no Redis local (cartas, layouts e ícones) para o de produção, lido do `.env.production.local` (só local: `KV_REST_API_URL` e `KV_REST_API_TOKEN` da Vercel). Mostra o que vai mudar e pede confirmação (`--dry-run` só mostra; `--yes` não pergunta). Cada item trocado guarda a versão anterior no histórico de produção. Item editado pelo site depois do último envio fica de fora, para não desfazer a edição de alguém (`--overwrite` envia mesmo assim). As imagens não vão por aqui (`src/lib/content/push.ts`).
- **Scripts locais** (scan, apply, clean_elements, dump_set) leem e gravam o conteúdo do Redis das variáveis do `.env.local` (`loadContentForScripts` em `src/lib/content/scripts.ts`, com `node --env-file-if-exists=.env.local`). Por padrão é o Redis local do Docker; para gravar em produção, use as variáveis de produção.

## Cartas

O catálogo tem todas as coleções, com as imagens e a lista oficial do [CCG Trader](https://www.ccgtrader.net/games/naruto-ccg). Os dados de cada carta são conferidos contra a imagem e ficam em inglês, como impressos, em `src/data/sets/`; o app mostra e edita os textos em PT-BR, no conteúdo do jogo (ver "Textos em PT-BR").

- Imagens originais: `cards/<set>/<id>.png`, já sem marca d'água, onde o id é o código oficial em minúsculas (ex.: `cards/s01/s01-n-001.png` = set S01, Ninja 001). **Ficam só na máquina local** (fora do Git pelo `.gitignore`, ~1,7 GB); o repositório guarda apenas as versões otimizadas de `public/cards/`.
- Dados: no conteúdo do jogo, no Redis (ver "Conteúdo do jogo"); a carga inicial é um arquivo por coleção em `src/data/sets/` (ex.: `s01-the-path-to-hokage.ts`); nomes e códigos das coleções em `src/data/sets.ts`.
- **Textos em PT-BR:** o app mostra as cartas em PT-BR: nomes (Jutsus, Missões e Ninjas descritivos), efeitos, frases, características, Atributos de Combate e coleções. É o texto guardado no conteúdo do jogo (Redis), editado pela aba **Editar** do detalhe da carta. O texto em inglês, como impresso, fica fixo no código (`src/data/sets/`), sem edição, e é a fonte da revisão contra as imagens. A tradução de `src/data/ptbr/` (uma por coleção + glossário, ver [docs/TRADUCAO.md](docs/TRADUCAO.md)) só faz a carga inicial. As regras leem os termos em PT-BR ("Esquadrão", "Reforço", "Nome: X"), e também os impressos, das cartas criadas; o kanji do Atributo de Combate é achado pelo nome em PT-BR.
- Se alguma imagem de `cards/` mudar, rode `npm run cards:images` para gerar os WebP em `public/cards/<set>/` (tamanho cheio, usado no detalhe da carta) e `public/cards/<set>/thumbs/` (miniatura, usada nas grades). Para gerar só algumas coleções, passe as pastas: `npm run cards:images -- s01 s07` (recria só `public/cards/s01/` e `public/cards/s07/`; sem argumentos, recria tudo). O app monta o caminho com `cardImageUrl` (`src/models/card.ts`).
- **Cartas montadas:** as cartas já escaneadas têm `layout` nos dados (`CardLayoutInfo` em `src/models/cardLayout.ts`): o layout (moldura, painel e posições), o design alternativo (se houver), o ajuste da fonte do nome (`nameSize`, em px sobre o tamanho do layout: negativo diminui, positivo aumenta, 0 = o do layout; o mesmo campo existe no criador; a aba **Editar** do detalhe da carta ajusta esse tamanho, e o detalhe em **Montada** também mostra um atalho que grava `nameSize`), os ícones impressos (`icons`: tipo, variante de cada elemento, ícones de custo e moldura do Atributo de Combate) e o enquadramento das artes extraídas. Os ícones ficam na carta, e não no layout, porque as coleções mais novas misturam ícones de layouts diferentes. As artes ficam em `card-layouts/arts/<set>/<id>/` (só local): `back.png` fica atrás da moldura e `front.png` (opcional, com transparência) na frente da moldura e atrás do painel. `npm run cards:layouts` gera os WebP em `public/card-layouts/arts/<set>/<id>/`. O scan (`python -I scripts/card-scan/scan.py s01-n-001 s01-j-001`) identifica o layout comparando a carta com as molduras e painéis de cada layout, identifica os ícones comparando as variantes de cada um na posição do layout (lida do conteúdo do jogo pelo Node), calcula o enquadramento das artes (pontos SIFT + ajuste fino) e grava uma montagem de conferência em `.tmp-card-scan/`. Ele imprime o trecho `layout: {...}` de cada carta e grava um `scan.json`. O enquadramento é o mesmo do criador (`x`, `y` e `zoom` sobre o "cobrir" da carta de 750×1050). O site mostra as cartas com a imagem impressa por padrão; o toggle **Originais | Montadas** da listagem (catálogo e montador, ao lado da contagem) troca as grades para as cartas montadas, nas coleções escaneadas (preferência no localStorage, `naruto-ccg:card-design`, em `src/lib/cardDesign.ts`). No detalhe da carta, que abre no design escolhido, **Original | Montada** alterna entre a imagem impressa e a carta montada; `/criar/calibrar?ids=s01-n-001,s01-j-001` mostra a comparação lado a lado. As coleções S01 a S22 estão escaneadas, ainda sem artes extraídas. S01–S10 são todas do layout 1 (da S02 à S10 com `--layout layout-01 --skip-icons`, que não identifica os ícones e deixa os padrão do layout). S11–S22 são do layout 2 (elementos na variante 02, o Vazio na 01; custos e Atributo de Combate os padrão do layout), mas a partir da S13 há cartas fora do padrão, conferidas uma a uma: layout 4 (Squad, roxo; Reinforcement, padrão), layout 3 (arte inteira com o painel escuro embaixo; 7 com a borda vermelha) e layout 5 (só a faixa de características, sem texto de efeito; elementos na variante 03). Nelas o tipo é o alternativo nos layouts 3 e 5, e o Atributo de Combate foi identificado pelo scan. `node --env-file-if-exists=.env.local scripts/card-scan/apply.ts <scan.json> [<scan.json> ...]` grava o resultado no conteúdo do jogo, nas cartas que ainda não têm `layout` (o último scan de cada carta vale; `--replace` troca o das que já têm): as cartas usam a própria carta impressa como arte de fundo (`print: true` no enquadramento, gerado pelo scan quando a carta não tem arte em `card-layouts/arts/`), com a moldura, o painel e os textos montados por cima (a frase é desenhada de novo, no idioma escolhido, com um sombreado em volta das letras que apaga de leve a impressa no fundo: `printedFlavor` na carta do criador, que dá para desligar no editor). Ao extrair a arte de uma carta, rode o scan de novo e troque o `art` dela (`--print` ignora as artes extraídas e volta para a impressa).
  - **Impressa sem os elementos:** `tools/.venv-upscale/Scripts/python.exe -I scripts/card-extract/clean_elements.py <ids>` apaga os ícones de elemento (disco + nome de lado) da impressa com o LaMa, nas posições do layout e com os elementos dos dados, e grava em `.tmp-card-extract/clean-elements/` (com a comparação em `_compare/`). As aprovadas na conferência visual vão para `card-layouts/arts/<set>/<id>/print-clean.png` e ganham `clean: true` ao lado do `print: true` (o scan põe sozinho quando o arquivo existe); a carta montada usa essa imagem, no mesmo enquadramento, com o elemento montado por cima. O LaMa pode apagar ou borrar desenho que passava por baixo do ícone; mesmo assim a versão limpa é usada (os defeitos são ajustados aos poucos). A S01 inteira está limpa.

## Roadmap

- **MVP 1 (pronto)** — lista de cartas com filtros e montagem de decks salvos no localStorage.
- **MVP 2 (pronto)** — compartilhamento por código (API + Redis, como no projeto pokedex): um deck ou a coleção inteira, importável em outro navegador.
- **MVP 3 (pronto)** — salas de jogo: criar uma sala, enviar o código (UUID) para um amigo entrar e, dentro da sala, escolher os decks e marcar "Pronto". Especificação em [docs/SALAS.md](docs/SALAS.md).
- **MVP 4 (próximo)** — a partida em si, dentro da sala (motor do jogo no servidor, cada jogador vê só o que pode ver).
- **Depois** — cartas montadas dinamicamente (criador pronto para os 5 layouts das coleções).

## Estrutura

- `docs/` — documentação: regras (`REGRAS.md`, `Regras Naruto CCG.md/.html`, manuais em PDF e imagens em `rules-img/`), publicação (`DEPLOY.md`) e especificação das salas de jogo (`SALAS.md`).
- `src/data/cards.ts` — catálogo das cartas em uso (preenchido com o conteúdo do Redis); `src/data/sets/` — carga inicial do catálogo.
- `src/lib/content/` — conteúdo do jogo (cartas, layouts, ícones e imagens) no Redis e no Blob: tipos, carga (`hydrate.ts`, `ContentProvider.tsx`, `server.ts`), edições e histórico (`changes.ts`, `store.ts`), imagens (`assets.ts`, `assetStore.ts`) e as rotas em `src/app/api/content/`.
- `src/lib/deckRules.ts` — regras de montagem do rulebook PT-BR (`docs/Naruto CCG - Rulebook PTBR.pdf`, p. 10 e 43–44): exatamente 50 cartas, qualquer quantidade de cada tipo e **até 3 cópias de cada carta**, contadas pelo id (cartas diferentes com o mesmo nome contam separado; o rulebook limita por nome). A característica `Name: X` vale só em jogo (`getInPlayNames` em `src/models/card.ts`). Também cuida do Baralho de Reforço (`docs/REGRAS.md` 4.17): cartas com a característica `Squad` ou `Reinforcement` (`isReinforcementCard`) vão para ele, não para o Deck; são até 15 e não contam nas 50. E da parte **Tokens**: só cartas com `token: true` (`isTokenCard`; nenhuma carta impressa é Token por enquanto), quantas quiser, mas 1 cópia de cada, fora das 50, do Reforço e do limite de 3; por enquanto ficam fora da partida nas salas (`createGame` não as coloca em nenhuma zona). As três partes ficam no mesmo mapa `cards` do deck e `deckPartOf` diz a parte de cada carta.
- `src/lib/cardFilters.ts` — busca, filtros e ordenação do catálogo (pelos textos do conteúdo, em PT-BR).
- `src/data/ptbr/` — tradução PT-BR (por coleção + glossário), a carga inicial dos textos do conteúdo (`src/lib/content/ptbr.ts`); o glossário também dá os nomes das coleções (`src/lib/setName.ts`).
- `src/lib/deckStore.ts` — decks no localStorage (`naruto-ccg:decks`, com `version` para migrações); gravação só via `deckActions.save`.
- `src/lib/useLeaveGuard.ts` — aviso de alterações não salvas ao sair do montador.
- `src/lib/deckShare.ts`, `src/lib/shareClient.ts`, `src/lib/redis.ts` e `src/app/api/shares/` — compartilhamento por código.
- `src/lib/rooms/` e `src/app/api/rooms/` — salas de jogo (regras puras em `model.ts`, Redis em `store.ts`, navegador em `client.ts`/`useRoom.ts`).
- `src/lib/cardMaker/` e `src/components/cardMaker/` — criador de cartas: modelo e marcação do texto (`model.ts`), configuração de cada layout (`layouts/`: `types.ts`, `shared.ts` com as funções que posicionam os ícones, `index.ts` com os layouts em uso e `seed.ts` + `layoutXX.ts` com a carga inicial), configuração de cada ícone (`icons/`: `index.ts` com os ícones em uso e `seed.ts` + um arquivo por ícone com a carga inicial; vilas e kanjis de custo, sem texto, em `village.ts` e `cost-element.ts`), localStorage (`store.ts`) e a carta montada em HTML (`CardRender.tsx`, desenhada em 750×1050 e escalada).
- `card-layouts/` — elementos visuais extraídos das cartas (molduras por layout, ícones e exemplos). O app usa as versões WebP de `public/card-layouts/`, geradas por `npm run cards:layouts`. Ícones em tela padronizada (tipo, custo, Atributo de Combate) são posicionados pela tela; os demais são recortados pela área útil.
- `src/app/` — páginas: `/` (Meus decks), `/cards` (catálogo), `/decks/[id]` (montador), `/jogar` e `/salas/[id]` (salas), `/criar` (criador de cartas). Componentes em `src/components/`.
- `compose.yaml` — Redis local para desenvolvimento; `vercel.json` — região das funções (`gru1`, São Paulo).
- `scripts/review-set/` — revisão de coleções e frases (ver `docs/REVISAO-CARTAS.md`). **Só local**, fora do Git.
