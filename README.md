# Naruto CCG Digital

Esse projeto é uma versão digital do clássico Naruto CCG (publicado entre 2006 a 2013 pela Bandai). A ideia do projeto é funcionar como um "Pokemon TCG Live" para Naruto CCG, que possa ser rodado diretamente no navegador, já que a ideia é usar para jogar entre amigos.

Hoje o app tem o catálogo de cartas e o montador de decks: o jogador monta quantos decks quiser com as cartas disponíveis, seguindo as regras de montagem do jogo original. Os decks e as cartas criadas ficam na nuvem (Redis), ligados ao **código da conta** do jogador (ver "Decks e cartas na nuvem"), e os decks podem ser compartilhados por um código (UUID), como no projeto pokedex.

Publicado em <https://naruto-ccg.vercel.app> (deploy automático a cada push na `main`). O acesso é protegido por senha quando a variável `SITE_PASSWORD` existe: o navegador pede uma vez (`/entrar`) e guarda o acesso num cookie de 1 ano (`src/middleware.ts`, `src/lib/sitePassword.ts`; ver [docs/DEPLOY.md](docs/DEPLOY.md#senha-de-acesso)).

Na pasta `docs/` estão os manuais oficiais (PDF), as regras consolidadas (`docs/REGRAS.md`), o guia de publicação (`docs/DEPLOY.md`), o processo de revisão das cartas contra as imagens e das frases (`docs/REVISAO-CARTAS.md`), as convenções da tradução PT-BR (`docs/TRADUCAO.md`) e a especificação da próxima etapa, as salas de jogo (`docs/SALAS.md`).

A ideia futuramente é ter um layout dinâmico para as cartas, com o sistema "montando" a carta virtualmente usando o layout + ícones + descrições + tipagens + efeitos. Por enquanto as cartas usam as imagens oficiais, com tipos, custos e efeitos cadastrados.

## Como rodar

Requer Node.js e Docker (para o Redis local).

```bash
npm install
cp .env.example .env.local   # só na primeira vez
npm run dev                  # sobe o Redis local (Docker) e o app em http://localhost:3000
npm test                     # regras de montagem, conversões das cartas, compartilhamento e salas (com cartas inventadas)
npm run type-check
npm run services:down        # derruba o Redis local
npm run cards:layouts        # recria public/card-layouts a partir de card-layouts/ (molduras e ícones do criador de cartas e artes das cartas escaneadas)
npm run content:sync-cards -- S02   # copia cartas de src/data/sets/ (+ tradução) para o conteúdo no Redis (ver "Conteúdo do jogo")
```

Com o Redis local vazio, a primeira abertura do app grava nele a carga inicial (as cartas de `src/data/sets/` e os layouts e ícones de `src/lib/cardMaker/`).

Publicação (Vercel + Upstash): ver [docs/DEPLOY.md](docs/DEPLOY.md).

## Funcionalidades

- **Cartas** (`/cards`): catálogo com busca por nome (em PT-BR ou no inglês impresso), característica ou efeito, filtros por coleção, tipo (e Token) e elemento, ordenação e detalhe de cada carta. No celular, a busca fica presa no topo com o botão **Filtros** (coleção, tipo, elemento e ordenação num painel que sobe de baixo) e os filtros ativos aparecem como chips removíveis. A grade e o detalhe mostram sempre a imagem impressa de cada carta, com os dados e os textos (PT-BR) do conteúdo do jogo.
- **Meus decks** (`/`): criar, editar, duplicar, excluir, compartilhar e importar decks, e o **Código da conta** (ver "Decks e cartas na nuvem").
- **Jogar** (`/jogar` e `/salas/<uuid>`): criar uma sala só com o apelido, enviar o código (ou o link) para um amigo e, dentro da sala, cada um escolhe o deck e marca **Pronto**. Quando os dois estão prontos, a sala abre a **arena** com os decks embaralhados e a mão inicial: cada um arrasta as próprias cartas entre as zonas, compra, embaralha e busca cartas no deck. Quem começa é sorteado; o Atacante avança as fases (Missão, Organização e Batalha, com **Próxima fase**) e **passa o turno** na Batalha, o que avança o Marcador de Turnos dele (as fases são só referência, sem as regras de cada uma). Ninjas podem ser virados para Ferido (tecla **R** sobre o Ninja; as teclas de atalho ficam no botão **⌨ Atalhos**), o Poder de cada Time pode ser ajustado com −/+, as cartas na mesa recebem moedas (Growth, +1/+1, Poison, as das Missões Permanentes (X) e qualquer outra impressa; as de Poder somam no Time), os Tokens do deck são baixados na Vila pelo botão **🧩 Tokens** (quantas cópias precisar), a **🪙 Moeda** Ninja é sorteada no servidor para os dois verem, o Marcador de Turnos tem −/+, Prêmios de Batalha podem ser devolvidos (↩), cartas do topo ou do fundo do Deck podem ser reveladas na Vila (👁) e clicar numa carta sua abre o detalhe com **Descartar** e os botões de mover. O **botão direito** abre um menu com o que dá para fazer com o elemento: numa carta sua, ver, ferir/curar, tornar Líder, mover o Time, Poder ±1, moedas e para onde ela pode ir; no seu Deck, comprar, buscar, embaralhar, revelar, dar o topo como Prêmio e devolver a mão; nos Descartes, ver a pilha; nos Prêmios, olhar e devolver (`ContextMenu` em `src/components/arena/GameArena.tsx`). A tela segue o design "Campo de Jogo" (palco de 1600×900 escalado para caber inteiro na janela). Prévia local em `/arena`. **Jogar sozinho** (`/jogar/sozinho`): um deck para cada lado e o jogador comanda os dois, no próprio navegador (**⇅ Trocar de lado**, automático ao passar o turno). Detalhes em [docs/SALAS.md](docs/SALAS.md).
- **Criar carta** (`/criar`): monta cartas nos layouts 1 a 5 a partir das molduras e ícones de `card-layouts/` (tipo, elementos, custos, vila, Atributo de Combate com o kanji tirado de `card-layouts/icons/attributes`, força, textos e frase), com a arte enviada pelo jogador (arraste para enquadrar). No texto de efeito, em qualquer tipo de carta, `~1~` (número ou `~X~`) vira o ícone do Chakra genérico com o valor e `~fire~` (ou `~fogo~`, `~water~`, `~agua~`...) o símbolo do elemento (`textIcon` em `src/lib/cardMaker/model.ts`). **Ajustar posições** (abaixo da prévia) mostra as caixas dos elementos na carta (nome, ícones, custos, textos...) para arrastar e redimensionar como no editor de layouts, mas só nesta carta: os ajustes ficam na carta (`layoutOverrides`, aplicados por `cardLayout` em `src/lib/cardMaker/layouts/index.ts`), o layout não muda, **Voltar às do layout** desfaz e trocar de layout apaga (`src/components/cardMaker/CardPositionEditor.tsx`; não aparece nas alters). A **linha acima do texto** (traço de pincel que separa o texto de efeito do nome e das características) é desenhada pela carta montada, sempre logo acima da caixa de texto e com a largura dela (`TextDivider` em `CardRender.tsx`; `textDivider` no layout, com o padrão `TEXT_DIVIDER_DEFAULT` enquanto o layout não tem o seu; a cor é o campo `textDividerColor` de cada layout, uma por tipo de carta (cada tipo tem o seu painel), definida em **Cor da linha acima do texto** no editor de layouts com o tipo da prévia, e o tipo sem cor usa o vermelho `TEXT_DIVIDER_COLOR`); o criador tem o liga/desliga por carta, e a distância e a largura mudam em **Ajustar posições**. Dá para partir de uma carta do catálogo (**Importar do catálogo** ou `/criar?importar=<id>&layout=layout-02`): o criador pergunta se é uma **carta nova** (os dados vêm preenchidos, tudo fica editável e a carta salva não tem ligação com a do catálogo; a imagem original fica para comparar) ou uma **alter** (ver "Design das cartas e alters"). As edições ficam num rascunho e só são gravadas no botão **Salvar**, que envia a arte para o Vercel Blob e guarda a carta na nuvem (ver "Decks e cartas na nuvem");  sair com alterações não salvas pergunta o que fazer, como no montador. Cada layout tem a sua configuração (no conteúdo do jogo, no Redis; ver "Conteúdo do jogo"), onde cada ícone tem só a posição e o tamanho (`{ x, y, size }`); o resto do ícone (proporção, nome de lado, números de custo e de força, nome e kanji do atributo) fica na configuração de cada ícone, relativa ao próprio ícone, para ficar igual em todos os layouts. A página `/criar/calibrar?layout=layout-02&ids=...` mostra lado a lado a carta montada, a original e as duas sobrepostas. **Editar layouts** (`/criar/layouts`, link no Criar carta) edita essas configurações, para todo mundo e sem deploy, em duas abas. **Layouts**: escolhe o layout, o tipo e uma carta de exemplo (com a original por cima), arrasta as caixas de cada ícone e texto na carta (o canto muda o tamanho; as setas movem a selecionada) ou mexe nos campos; muda o nome do layout, os ícones que ele usa por padrão (variante dos elementos, custos de entrada e de mão, moldura do Atributo de Combate) e as imagens (moldura e painel de cada tipo). **+ Novo layout** cria um layout cópia do aberto (molduras, painéis, posições e ícones), com id `layout-<nome>`; enquanto uma imagem dele ainda é a do layout base, **Trocar imagem** grava a nova em `<id do layout>/` e o layout passa a usá-la. **Excluir layout** (só os criados no editor, e só se nenhuma carta o usa) apaga o layout e as imagens dele do Blob (`src/app/api/content/layouts/`). **Ícones**: cada ícone (tipo, tipo alternativo, elemento, custo, Chakra, Atributo de Combate) numa carta de exemplo, só com as caixas de dentro dele, e os campos dele (posição, tamanho, cor e alinhamento dos textos e números, contorno, sombra), que valem em todos os layouts (`src/components/cardMaker/IconsEditor.tsx`). No Atributo de Combate, **Atributos no exemplo** mostra a carta com 1 atributo (kanji e nome), 2 (os dois kanjis lado a lado com "/" no meio e os nomes um acima do outro, medidas em `pair` do ícone) ou 3 (só os nomes), e **"?" (só o símbolo)**: o atributo que é só um símbolo tem posição e tamanho próprios (`symbol`: `dx`, `dy`, `size`), então mover o "?" não mexe no kanji dos atributos com nome. Quando o Atributo de Combate invade a caixa do texto de efeito, o texto contorna a silhueta dele (a parte opaca da imagem, calculada no navegador em `src/lib/cardMaker/silhouette.ts` e aplicada com `shape-outside`) e quebra a linha sozinho, em qualquer layout e com o mesmo texto; no ícone, **texto de efeito contorna o ícone** liga ou desliga e muda a distância (`textWrap`). **+ Novo ícone** cria uma cópia do ícone aberto com o próximo id livre do grupo: nova variante de um elemento (`element:fire-04`), novo custo de entrada ou de mão (`cost:entrance-05`), nova moldura do Atributo de Combate (`attribute:08`) ou, a partir de um ícone de tipo, um ícone alternativo do tipo, com nome (`type-variant:ninja-<nome>`); o Chakra genérico é um só. O ícone novo aparece nos seletores do criador, da aba Editar e do editor de layouts (as listas vêm do conteúdo: `entranceIcons`, `handIcons`, `attributeFrames`, `elementVariants`); a imagem dele vai para `icons/custom/` (a do ícone copiado fica como está). **Excluir ícone** só aparece nos criados no editor e só exclui se nenhuma carta do catálogo nem layout o usa; a imagem sai do Blob (`src/lib/content/icons.ts`, `src/app/api/content/icons/`). Uma carta criada que usava um ícone excluído passa a mostrar o primeiro do mesmo tipo. Tipo, elemento e custo têm uma **caixa** de tamanho fixo (a largura vem do layout; a altura é a largura × a proporção do ícone, `aspect`) e a imagem é enquadrada dentro dela (`art`: canto e largura, arrastando a caixa "Imagem do ícone" na carta); **Usar em todos do grupo** deixa a mesma caixa em todo o grupo (ex.: todos os custos de entrada e de mão), para padronizar os ícones. O **alinhamento** (esquerda, centro, direita; `align` em `src/lib/cardMaker/icons/types.ts`) diz se o texto começa, fica centrado ou termina no ponto dele. **Trocar imagem** troca a moldura, o painel ou a imagem de um ícone (WebP ou PNG, até 2 MB, para o Vercel Blob; a anterior é apagada de lá). Nos ícones com caixa, a imagem nova pode ter qualquer tamanho: ela é encaixada inteira na caixa e quem enviou ajusta o enquadramento antes de salvar. Nas molduras, nos painéis, no Chakra e no Atributo de Combate (medidos na própria imagem), a imagem nova precisa ter o tamanho da que ela substitui (molduras e painéis 1060×1484, Atributo de Combate 680×670); o editor mostra o tamanho e recusa outro, para quem envia redimensionar antes. O menu do topo tem **Layouts**, que abre o editor. **Voltar para a do deploy** apaga do Blob a imagem trocada, e **Histórico** volta uma das últimas 5 versões de um layout, ícone ou carta (as imagens não têm histórico: no Blob só fica o que está em uso, ver "Conteúdo do jogo"). Um valor igual em vários tipos de carta (no código original, `forAllTypes` e constantes) muda em todos eles (`linkSharedTypes` em `src/lib/content/changes.ts`). O **Salvar** grava via `/api/content/config`. O detalhe de toda carta do catálogo tem a aba **Editar** (`src/components/cardMaker/CardEditTab.tsx`, `CardDataEditor` em `CardEditor.tsx`): só os textos (nome, efeito com a marcação, frase, características, Atributo de Combate) e os números (custos de entrada e de mão, poder saudável e ferido; nos Jutsus, o custo: quais ícones de elemento e quantos de cada, e o Chakra genérico com um número, inclusive os custos alternativos), sem o design, ao lado da imagem impressa. A carta é convertida para carta do criador e de volta (`src/lib/cardMaker/catalogEdit.ts`), e o **Salvar** grava na carta do conteúdo do jogo (`PUT /api/content/cards/<id>`, conferida em `src/lib/content/cardValidation.ts`). Qualquer um com a senha do site pode editar.
- **Montador** (`/decks/<id>`): cartas disponíveis à esquerda, com +/− em cada uma, e o deck à direita (por tipo, mais as abas Reforço e Tokens, com contagem e validação das regras). No celular, o deck fica numa barra presa embaixo (contagem e validade); tocar nela abre o deck num painel que sobe de baixo, por cima da lista, e ao fechar a lista continua no mesmo ponto (`src/components/DeckSheet.tsx`).
  - **Imprimir deck** gera um PDF A4 (9 cartas por folha, tamanho real). Cada carta sai como está no deck: a imagem impressa ou, com uma alter escolhida, a carta montada; as cartas criadas saem sempre montadas (o desenho das montadas fica em `src/components/cardMaker/cardImageRenderer.tsx`).
  - **Design de cada carta no deck:** o 🎨 de cada carta do deck escolhe o design dela só neste deck: a **Original** (a impressa, o padrão) ou uma das alters dela, de qualquer jogador (`src/components/DeckDesignDialog.tsx`, rota `/api/versions`). Fica no deck (`Deck.designs`: id da carta → id da alter) e vale na tela, na impressão, nas salas (os dois jogadores veem a alter escolhida pelo dono do deck) e no Jogar sozinho (`src/lib/deckDesigns.ts`).
  - As cartas do **Criar carta** também aparecem (coleção **Cartas criadas** no filtro; as alters não, porque são designs de uma carta do catálogo) e seguem as mesmas regras de montagem, lidas dos campos do criador (`src/lib/cardMaker/deckCard.ts`; no deck, o id é `custom-<id da carta>`). Decks com cartas criadas podem ir para as salas e ser compartilhados por código: as cartas vão junto com o deck (e quem importa um código antigo fica com as que ainda não estão na nuvem) e as artes ficam no Vercel Blob (ver [docs/SALAS.md](docs/SALAS.md#cartas-criadas) e [docs/DEPLOY.md](docs/DEPLOY.md#artes-das-cartas-criadas-vercel-blob)). Toda arte enviada é tratada antes (até 1050 px, WebP, até 300 KB). O detalhe da carta tem **Excluir carta permanentemente** (só nas suas): ela sai do criador e dos seus decks, e a arte é apagada do Blob se nada mais a usa. O detalhe da carta tem o link **Editar no criador** (`/criar?carta=<id>`).
  - As alterações ficam num rascunho e só são gravadas no botão **Salvar**.
- **Design das cartas e alters:** as cartas do catálogo mostram sempre a imagem impressa, no catálogo, no detalhe e no montador; não há design padrão. O visual montado fica nas **alters**: cartas do **Criar carta** ligadas a uma carta do catálogo (`CustomCard.source`), guardadas na nuvem e listadas em `naruto-ccg:versions:<carta>`. Para criar uma, **Importar do catálogo** no Criar carta e escolher **Criar uma alter**: os dados e os textos ficam travados (os da carta) e mudam só o layout (entre os que têm o tipo da carta), a moldura do Atributo de Combate (Ninja) e as artes (fundo e frente, com o enquadramento), e **Ajustar caixas de texto** (abaixo da prévia) muda a posição e o tamanho da caixa do texto de efeito e da das características só nesta alter (`layoutOverrides`, que vai junto para o design no deck) (`mode="alter"` no `CardEditor`); a alter precisa de uma arte para salvar. A alter não é uma carta do deck: só é escolhida no 🎨 do montador (ver acima). Ela monta a carta com o visual dela e os dados e textos atuais da carta (`designLayout` em `src/lib/cardMaker/catalogEdit.ts`). Excluir a alter no Criar carta tira ela dos seus decks.
  - Ao sair com alterações não salvas (links do app ou "voltar" do navegador), o app pergunta se quer **Salvar**, **Descartar** ou continuar editando. Ao fechar ou recarregar a aba, aparece o aviso padrão do navegador.

## Decks e cartas na nuvem

Os decks (`naruto-ccg:decks:<dono>`, `src/lib/decks/`) e as cartas do **Criar carta** (`naruto-ccg:custom-cards`, `src/lib/customCards/`) ficam no Redis; nada disso fica no navegador. O dono é a identidade anônima do navegador (`naruto-ccg:player` no localStorage, a mesma das salas): o servidor guarda só o hash do token. O **Código da conta** (em Meus decks, `src/components/AccountDialog.tsx`) mostra esse token para abrir os mesmos decks e cartas em outro navegador; quem limpa os dados do navegador sem guardar o código perde o acesso.

- O navegador carrega tudo uma vez (`GET /api/me`: os decks, as cartas do jogador e as de outros que os decks usam ou escolheram como design) e grava em seguida a cada mudança (`/api/me/decks`, `/api/me/cards`), em `src/lib/cloud/library.ts`. Qualquer um lê qualquer carta criada pelo id (`/api/custom-cards?ids=`); só o dono grava e exclui.
- Ao gravar ou excluir uma carta criada, o servidor atualiza o uso das artes no Blob (`custom:<dono>:<id>`, `src/lib/customCards/keys.ts`). Excluir uma carta tira ela dos decks do dono.
- **Do navegador para a nuvem:** os decks e as cartas que estavam no localStorage (`naruto-ccg:decks`, `naruto-ccg:custom-cards`) são enviados uma vez (`/api/me/import`) e apagados do navegador, junto com chaves antigas sem uso. As artes que ainda estavam só no navegador vão para o Blob antes.
- No localStorage ficam só a identidade (`naruto-ccg:player`), a partida do Jogar sozinho (`naruto-ccg:solo-game`), o tema da arena e o design da impressão.

## Compartilhar decks

Para passar decks para um amigo, a tela **Meus decks** tem:

- **Compartilhar** (em cada deck) e **Compartilhar coleção** (todos os decks): enviam uma cópia para o servidor, que grava no Redis e devolve um UUID.
- **Importar**: busca o UUID e adiciona os decks como novos (não apaga nada).

O código é um retrato do momento: editar o deck depois não muda o que foi compartilhado. Mesmo esquema do projeto pokedex: `@upstash/redis` (API REST da Upstash); local via `compose.yaml` (Redis + `serverless-redis-http` nas portas 6381/8078).

- O cliente lê `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` **ou** `KV_REST_API_URL`/`KV_REST_API_TOKEN`. Em produção são as `KV_*`, criadas pela integração Upstash da Vercel.
- O banco de produção é **compartilhado com o projeto pokedex**, então toda chave gravada começa com `naruto-ccg:` (ex.: `naruto-ccg:share:<uuid>`). Mantenha esse prefixo em chaves novas.
- Código: `src/app/api/shares`, `src/lib/deckShare.ts` (validação), `src/lib/shareClient.ts`, `src/lib/redis.ts`.

## Conteúdo do jogo

As cartas (dados de jogo e o `layout` de cada uma), a configuração dos layouts e dos ícones e as imagens das molduras e ícones ficam fora do código, para serem editadas pelo site sem deploy (`src/lib/content/`):

- **Redis** (chaves `naruto-ccg:content:*`): `cards` (hash id → carta; o campo `set` é o código da coleção, um dos de `src/data/sets.ts`; sem visual: as cartas do catálogo mostram sempre a impressa; formato 4 em `naruto-ccg:content:format`), `layouts` (hash id → configuração do layout), `icons` (hash `<grupo>:<id>` → configuração do ícone, ex.: `element:fire-02`), `assets` (hash caminho da imagem → URL no Vercel Blob), `version` (aumenta a cada gravação) e `history:<tipo>:<id>` (as últimas 5 versões de cada carta, layout e ícone, para o **Histórico** dos editores).
- **Imagens:** a configuração guarda o caminho lógico (`/card-layouts/layout-02/jutsu-frame.webp`) e o mapa `assets` diz onde a imagem está no Blob (`naruto-ccg/card-layouts/<caminho>-<hash>.webp`, `src/lib/content/assetStore.ts`). Sem entrada no mapa, vale o arquivo de `public/card-layouts/` do deploy. **Enviar imagens do deploy para o Blob** (no editor de layouts) copia todas para o Blob de uma vez. Quem resolve o caminho é `assetUrl` (`src/lib/content/assets.ts`), usado pela carta montada.
- **Nada sobrando no Blob:** só fica guardada a imagem em uso. Trocar uma imagem de layout ou ícone apaga a anterior (por isso as imagens não têm histórico), **Voltar para a do deploy** apaga a trocada, e um envio que falhou no meio é apagado; **Apagar imagens sem uso** (no editor de layouts, e no fim do envio das imagens do deploy) apaga da pasta `naruto-ccg/card-layouts/` o que não está no mapa. As artes (`naruto-ccg/art/`, das cartas criadas e das enviadas pela aba **Editar** para cartas do catálogo) contam quem as usa (`naruto-ccg:art-refs:<sha256>`, `src/lib/artStore.ts`): a imagem sai do Blob quando a última carta que a usa troca de arte ou é excluída, e a enviada que ninguém passou a usar em 24 h é apagada.
- **Carga:** o navegador busca a versão em `/api/content` e o conteúdo em `/api/content/<versão>` (~2,8 MB, em cache para sempre no navegador e na CDN) antes de mostrar as telas (`ContentProvider`); os módulos `CARDS`/`CARDS_BY_ID` (`src/data/cards.ts`), `LAYOUTS` e os mapas de ícones começam vazios e são preenchidos no lugar (`hydrateContent`). No servidor, toda rota que usa o catálogo chama `ensureContent()` (`src/lib/content/server.ts`, que confere a versão no Redis no máximo a cada 15 s).
- **Carga inicial:** `src/data/sets/` (cartas) e os `seed.ts` de `src/lib/cardMaker/layouts/` e `icons/` (configuração calibrada) só servem para gravar o Redis quando ele está vazio e para os testes (`src/lib/content/testSetup.mts`). O app não lê esses arquivos. As cartas são gravadas com os textos em PT-BR (`cardsToPtBr` em `src/lib/content/ptbr.ts`: a tradução de `src/data/ptbr/` e o glossário). Corrigiu uma carta neles (revisão contra as imagens)? Leve para o Redis com `npm run content:sync-cards -- <SET ou ids>` (troca os dados e os textos, inclusive o que foi editado pelo site, e a versão anterior vai para o histórico; `--dry-run` só mostra o que mudaria). O formato do conteúdo fica em `naruto-ccg:content:format` (2 = textos em PT-BR; 4 = cartas sem visual); um Redis com um formato antigo é convertido na primeira leitura (do 2 ou 3 para o 4: tira o `layout` e o `design` das cartas e apaga as versões do site, dono `system`; as cartas dos jogadores ligadas a uma carta ficam como alters).
- **Scripts locais** (scan, apply, clean_elements, dump_set) leem e gravam o conteúdo do Redis das variáveis do `.env.local` (`loadContentForScripts` em `src/lib/content/scripts.ts`, com `node --env-file-if-exists=.env.local`). Por padrão é o Redis local do Docker; para gravar em produção, use as variáveis de produção.

## Cartas

O catálogo tem todas as coleções, com as imagens e a lista oficial do [CCG Trader](https://www.ccgtrader.net/games/naruto-ccg). Os dados de cada carta são conferidos contra a imagem e ficam em inglês, como impressos, em `src/data/sets/`; o app mostra e edita os textos em PT-BR, no conteúdo do jogo (ver "Textos em PT-BR").

- Imagens originais: `cards/<set>/<id>.png`, já sem marca d'água, onde o id é o código oficial em minúsculas (ex.: `cards/s01/s01-n-001.png` = set S01, Ninja 001). **Ficam só na máquina local** (fora do Git pelo `.gitignore`, ~1,7 GB); o repositório guarda apenas as versões otimizadas de `public/cards/`.
- Dados: no conteúdo do jogo, no Redis (ver "Conteúdo do jogo"); a carga inicial é um arquivo por coleção em `src/data/sets/` (ex.: `s01-the-path-to-hokage.ts`); nomes e códigos das coleções em `src/data/sets.ts`.
- **Textos em PT-BR:** o app mostra as cartas em PT-BR: nomes (Jutsus, Missões e Ninjas descritivos), efeitos, frases, características, Atributos de Combate e coleções. É o texto guardado no conteúdo do jogo (Redis), editado pela aba **Editar** do detalhe da carta. O texto em inglês, como impresso, fica fixo no código (`src/data/sets/`), sem edição, e é a fonte da revisão contra as imagens. A tradução de `src/data/ptbr/` (uma por coleção + glossário, ver [docs/TRADUCAO.md](docs/TRADUCAO.md)) só faz a carga inicial. As regras leem os termos em PT-BR ("Esquadrão", "Reforço", "Nome: X"), e também os impressos, das cartas criadas; o kanji do Atributo de Combate é achado pelo nome em PT-BR.
- Se alguma imagem de `cards/` mudar, rode `npm run cards:images` para gerar os WebP em `public/cards/<set>/` (tamanho cheio, usado no detalhe da carta) e `public/cards/<set>/thumbs/` (miniatura, usada nas grades). Para gerar só algumas coleções, passe as pastas: `npm run cards:images -- s01 s07` (recria só `public/cards/s01/` e `public/cards/s07/`; sem argumentos, recria tudo). O app monta o caminho com `cardImageUrl` (`src/models/card.ts`).
- **Cartas montadas:** as cartas do catálogo não têm `layout` (mostram sempre a impressa; o conteúdo descarta o campo, e `scripts/card-scan/apply.ts` está desativado). O `layout` só aparece na carta com uma alter escolhida no deck (montado da alter). O que vem abaixo descreve o formato e o scan, que continua disponível para conferência. A carta com `layout` tem nos dados (`CardLayoutInfo` em `src/models/cardLayout.ts`): o layout (moldura, painel e posições), o design alternativo (se houver), o ajuste da fonte do nome (`nameSize`, em px sobre o tamanho do layout: negativo diminui, positivo aumenta, 0 = o do layout; o mesmo campo existe no criador), os ícones impressos (`icons`: tipo, variante de cada elemento, ícones de custo e moldura do Atributo de Combate) e o enquadramento das artes extraídas. Os ícones ficam na carta, e não no layout, porque as coleções mais novas misturam ícones de layouts diferentes. As artes ficam em `card-layouts/arts/<set>/<id>/` (só local): `back.png` fica atrás da moldura e `front.png` (opcional, com transparência) na frente da moldura e atrás do painel. `npm run cards:layouts` gera os WebP em `public/card-layouts/arts/<set>/<id>/`. O scan (`python -I scripts/card-scan/scan.py s01-n-001 s01-j-001`) identifica o layout comparando a carta com as molduras e painéis de cada layout, identifica os ícones comparando as variantes de cada um na posição do layout (lida do conteúdo do jogo pelo Node), calcula o enquadramento das artes (pontos SIFT + ajuste fino) e grava uma montagem de conferência em `.tmp-card-scan/`. Ele imprime o trecho `layout: {...}` de cada carta e grava um `scan.json`. O enquadramento é o mesmo do criador (`x`, `y` e `zoom` sobre o "cobrir" da carta de 750×1050). `/criar/calibrar?ids=s01-n-001,s01-j-001` mostra a comparação lado a lado. O scan das coleções S01 a S22 (abaixo) foi feito, mas os resultados não estão mais nas cartas. S01–S10 são todas do layout 1 (da S02 à S10 com `--layout layout-01 --skip-icons`, que não identifica os ícones e deixa os padrão do layout). S11–S22 são do layout 2 (elementos na variante 02, o Vazio na 01; custos e Atributo de Combate os padrão do layout), mas a partir da S13 há cartas fora do padrão, conferidas uma a uma: layout 4 (Squad, roxo; Reinforcement, padrão), layout 3 (arte inteira com o painel escuro embaixo; 7 com a borda vermelha) e layout 5 (só a faixa de características, sem texto de efeito; elementos na variante 03). Nelas o tipo é o alternativo nos layouts 3 e 5, e o Atributo de Combate foi identificado pelo scan. `node --env-file-if-exists=.env.local scripts/card-scan/apply.ts <scan.json> [<scan.json> ...]` grava o resultado no conteúdo do jogo, nas cartas que ainda não têm `layout` (o último scan de cada carta vale; `--replace` troca o das que já têm): as cartas usam a própria carta impressa como arte de fundo (`print: true` no enquadramento, gerado pelo scan quando a carta não tem arte em `card-layouts/arts/`), com a moldura, o painel e os textos montados por cima (a frase é desenhada de novo, no idioma escolhido, com um sombreado em volta das letras que apaga de leve a impressa no fundo: `printedFlavor` na carta do criador, que dá para desligar no editor). Ao extrair a arte de uma carta, rode o scan de novo e troque o `art` dela (`--print` ignora as artes extraídas e volta para a impressa).
  - **Impressa sem os elementos:** `tools/.venv-upscale/Scripts/python.exe -I scripts/card-extract/clean_elements.py <ids>` apaga os ícones de elemento (disco + nome de lado) da impressa com o LaMa, nas posições do layout e com os elementos dos dados, e grava em `.tmp-card-extract/clean-elements/` (com a comparação em `_compare/`). As aprovadas na conferência visual vão para `card-layouts/arts/<set>/<id>/print-clean.png` e ganham `clean: true` ao lado do `print: true` (o scan põe sozinho quando o arquivo existe); a carta montada usa essa imagem, no mesmo enquadramento, com o elemento montado por cima. O LaMa pode apagar ou borrar desenho que passava por baixo do ícone; mesmo assim a versão limpa é usada (os defeitos são ajustados aos poucos). A S01 inteira está limpa.

## Roadmap

- **MVP 1 (pronto)** — lista de cartas com filtros e montagem de decks (hoje salvos na nuvem).
- **MVP 2 (pronto)** — compartilhamento por código (API + Redis, como no projeto pokedex): um deck ou a coleção inteira, importável em outro navegador.
- **MVP 3 (pronto)** — salas de jogo: criar uma sala, enviar o código (UUID) para um amigo entrar e, dentro da sala, escolher os decks e marcar "Pronto". Especificação em [docs/SALAS.md](docs/SALAS.md).
- **MVP 4 (próximo)** — a partida em si, dentro da sala (motor do jogo no servidor, cada jogador vê só o que pode ver).
- **Depois** — cartas montadas dinamicamente (criador pronto para os 5 layouts das coleções).

## Estrutura

- `docs/` — documentação: regras (`REGRAS.md`, `Regras Naruto CCG.md/.html`, manuais em PDF e imagens em `rules-img/`), publicação (`DEPLOY.md`) e especificação das salas de jogo (`SALAS.md`).
- `src/data/cards.ts` — catálogo das cartas em uso (preenchido com o conteúdo do Redis); `src/data/sets/` — carga inicial do catálogo.
- `src/lib/content/` — conteúdo do jogo (cartas, layouts, ícones e imagens) no Redis e no Blob: tipos, carga (`hydrate.ts`, `ContentProvider.tsx`, `server.ts`), edições e histórico (`changes.ts`, `store.ts`), imagens (`assets.ts`, `assetStore.ts`) e as rotas em `src/app/api/content/`.
- `src/lib/deckRules.ts` — regras de montagem do rulebook PT-BR (`docs/Naruto CCG - Rulebook PTBR.pdf`, p. 10 e 43–44): exatamente 50 cartas, qualquer quantidade de cada tipo e **até 3 cópias de cada carta**, contadas pelo id (cartas diferentes com o mesmo nome contam separado; o rulebook limita por nome). A característica `Name: X` vale só em jogo (`getInPlayNames` em `src/models/card.ts`). Também cuida do Baralho de Reforço (`docs/REGRAS.md` 4.17): cartas com a característica `Squad` ou `Reinforcement` (`isReinforcementCard`) vão para ele, não para o Deck; são até 15 e não contam nas 50. E da parte **Tokens**: só cartas com `token: true` (`isTokenCard`; nenhuma carta impressa é Token por enquanto; no Criar carta e na aba **Editar**, o checkbox **Token** abaixo do tipo), quantas quiser, mas 1 cópia de cada, fora das 50, do Reforço e do limite de 3; na partida (salas e Jogar sozinho) não entram no Deck: o botão **🧩 Tokens** da arena baixa quantas cópias o jogador quiser na Vila dele (`createToken` em `src/lib/game/state.ts`; só o dono vê a lista), e a cópia que sai da Vila e do Campo de Batalha deixa de existir. As três partes ficam no mesmo mapa `cards` do deck e `deckPartOf` diz a parte de cada carta.
- `src/lib/cardFilters.ts` — busca, filtros e ordenação do catálogo (pelos textos do conteúdo, em PT-BR).
- `src/data/ptbr/` — tradução PT-BR (por coleção + glossário), a carga inicial dos textos do conteúdo (`src/lib/content/ptbr.ts`); o glossário também dá os nomes das coleções (`src/lib/setName.ts`).
- `src/lib/deckStore.ts` — decks do jogador (na nuvem, via `src/lib/cloud/library.ts`); gravação só via `deckActions`. Servidor em `src/lib/decks/` e `src/app/api/me/`.
- `src/lib/customCards/` — cartas do criador na nuvem (dono, versões das cartas do catálogo); rotas `/api/me/cards`, `/api/custom-cards` e `/api/versions`.
- `src/lib/useLeaveGuard.ts` — aviso de alterações não salvas ao sair do montador.
- `src/lib/deckShare.ts`, `src/lib/shareClient.ts`, `src/lib/redis.ts` e `src/app/api/shares/` — compartilhamento por código.
- `src/lib/rooms/` e `src/app/api/rooms/` — salas de jogo (regras puras em `model.ts`, Redis em `store.ts`, navegador em `client.ts`/`useRoom.ts`).
- `src/lib/cardMaker/` e `src/components/cardMaker/` — criador de cartas: modelo e marcação do texto (`model.ts`), configuração de cada layout (`layouts/`: `types.ts`, `shared.ts` com as funções que posicionam os ícones, `index.ts` com os layouts em uso e `seed.ts` + `layoutXX.ts` com a carga inicial), configuração de cada ícone (`icons/`: `index.ts` com os ícones em uso e `seed.ts` + um arquivo por ícone com a carga inicial; vilas e kanjis de custo, sem texto, em `village.ts` e `cost-element.ts`), localStorage (`store.ts`) e a carta montada em HTML (`CardRender.tsx`, desenhada em 750×1050 e escalada).
- `card-layouts/` — elementos visuais extraídos das cartas (molduras por layout, ícones e exemplos). O app usa as versões WebP de `public/card-layouts/`, geradas por `npm run cards:layouts`. Ícones em tela padronizada (tipo, custo, Atributo de Combate) são posicionados pela tela; os demais são recortados pela área útil.
- `src/app/` — páginas: `/` (Meus decks), `/cards` (catálogo), `/decks/[id]` (montador), `/jogar` e `/salas/[id]` (salas), `/criar` (criador de cartas). Componentes em `src/components/`.
- `compose.yaml` — Redis local para desenvolvimento; `vercel.json` — região das funções (`gru1`, São Paulo).
- `scripts/review-set/` — revisão de coleções e frases (ver `docs/REVISAO-CARTAS.md`). **Só local**, fora do Git.
